# Listen Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Listen button on finished chat answers that starts talking at once: a short spoken walkthrough of the answer in a voice made on this computer, with the part being explained highlighted.

**Architecture:** The page numbers the answer's rendered blocks and sends them with the click. The host has the chat's fast model (or the chat's local model) write a walkthrough as `<piece for="n">` pieces, splits them into sentences, and has a voice helper process (like Whisper's) turn each sentence into audio. The audio goes only to the pane that clicked, where Web Audio plays the sentences back to back. Only the walkthrough's text is saved, on the message (`msg.listen`).

**Tech Stack:** Plain JavaScript, no build step, no npm runtime dependencies. ONNX Runtime (WebAssembly or Node-API, decided by the spike) in a helper started with `ELECTRON_RUN_AS_NODE`. Web Audio in the chat webview. Tests are plain `node` scripts with `assert` (`test/*.test.js`, run by `npm test`).

**Spec:** `docs/superpowers/specs/2026-10-21-listen-design.md`

## Global Constraints

- `extension/` stays plain JavaScript with no npm dependencies at runtime; every `lib/listen/` file except `index.js` has no `require("vscode")`.
- No emoji anywhere. Page icons are Codicons via `icon("name")`. Pages can't use `style="…"` attributes (CSP): set `el.style` in script.
- UI words: the button is "Listen"; Kural is "Kural", never "Claude", except where it means Claude.
- First-use pop-up, exact: "Listen needs a voice: about N MB, downloaded once. The voice is made on this computer; the walkthrough's words are written by <model> from this answer." (N = the chosen engine's real total size; <model> = the short name of the model that will write it.)
- Every downloaded file is pinned by size and SHA-256 in code. A wrong hash deletes the file and fails.
- Walkthrough: 150–250 words; first sentence under 12 words; input at most 12,000 characters; a code block cut to its first 40 lines; a table to its first 20 rows; at most one expression tag per piece.
- No piece within 15 s → stop with "Couldn't write the walkthrough. Try again."
- The model that writes it: a chat on a local model uses that model; otherwise `brain.fastestModel(<chat's model>, ["codex"])`. Codex is never used. With no usable model: "Listen needs Claude, Gemini or a model on this computer to write the walkthrough."
- Voice helper: `process.execPath`, env `ELECTRON_RUN_AS_NODE=1`, first argument `--no-liftoff`, threads `min(8, max(1, availableParallelism() - 1))`, stops after 5 idle minutes. A crash fails one request only.
- Host → page Listen messages go only to the pane that started it (`postTo(pane, …)`), never `post()`.
- One Listen at a time per window. Only a finished walkthrough is saved (`msg.listen = { pieces: [{ block, text }], model, engine, at }`).
- Not in a read-only chat from another workspace (`tab.visiting`).
- `lib/chat/guide.js` and `docs/wiki/` change in the same pull request; a line in `RELEASE_NOTES.md` under "## Not released yet".
- Work on the branch `feat-listen-spec` (already has the spec). Never commit to `main`.

## Review Focus

1. An answer whose text is all inside the steps dropdown, or is empty: clicking Listen should say "Nothing to explain in this answer." and not wait forever. (Task 8 test.)
2. Clicking Listen again on the answer that is preparing or playing: it stops (the button is a toggle), never two jobs for one answer. (Task 7 test.)
3. A huge answer (30,000 characters, a 300-line code block): it is cut to the limits and still explained, no error. (Task 3 test.)
4. The model ignores the format (bullets, `code`, markdown, an emoji, a stray `<laugh>` the engine can't say): the voice never says symbols or tag names. (Task 2 test.)
5. The voice files deleted or damaged between sessions: Listen asks to download again instead of starting a helper that crashes. (Task 7 test.)
