# Memory and CPU: what Kural uses, and what changed (8 Oct 2026)

Adithya: "Since we have a lot of local models running and multiple requests, make sure Kural is not very memory hungry."
This is the measurement, what was changed right away, and a plan for later.

## How it was measured

- `node scripts/bench-memory.js` (read-only: `ps`, `top`, Ollama's `/api/ps`): every process of a running Kural (the app
  and everything it started), grouped by what it is. Each `claude` process is named by what it's for (it reads the
  system prompt the process was started with). Memory = macOS "footprint" (what Activity Monitor shows); CPU = % of one
  core over the measuring time (100 % = one core busy). `--list` shows every process, `--json` the raw numbers.
- Apple M5, 16 GB, macOS 27; Kural 1.1.0-alpha.6 (VS Code 1.135); Claude Code 2.1.289; Ollama 0.35.0.
- Two Kurals: **Adithya's running one** (looked at only, nothing touched; measured while this work's own Opus chat ran in
  it), and **a test copy** with a fresh profile set up like his: Tab Completion engine "Local model"
  (qwen2.5-coder:1.5b-base), Model Router helper Qwen3, Claude logged in.
- Numbers move by about ±50 MB between runs (renderers, the shared process): compare the big differences.

Where it goes, idle: renderers 320 MB, language servers 249, Tab's Claude processes 208, Ask's Claude process 107,
shared process/terminal host/file watcher 111, GPU 98, main 87, extension host 76.

While a chat streams: the chat page's own renderer ~15 % of a core, the GPU 9 %, the window 4 %, the extension host
2 %, the chat's `claude` 4-5 %. The extension host is nearly idle: a CPU profile over a 30 s answer was 29.3 s idle, its
longest busy stretch 9 ms.

A 9B model at a 32k context takes 7.8 GB on a 16 GB Mac: Ollama unloaded Tab's model to load it.

## Tab Completion while a chat answers

(Adithya: "When my chat is thinking, Tab Completion is not working.")

| | Tab's local model answers in |
|---|---|
| nothing else running | 60-140 ms (one line), 300-600 ms (a few lines) |
| a chat answering with a model on this computer | 2.0-3.2 s (one GPU for both; the chat's 9,600-token prompt took 28 s to read) |
| first suggestion after Ollama loaded the chat's model | 6.4 s (Tab's model had been unloaded; Kural gave up at 6 s) |
| now, with Claude helping while Ollama is busy | 0.6-1.3 s |

With a chat on Claude, Tab kept working (0.3-1 s) in every test. The one freeze found: the first chat answer of each
window stopped the extension host for 0.3 s (up to 8 s) while Kural asked `claude` which options it knows; that answer is
now saved per Claude Code version and asked in the background at startup.

## Changed now

| What | Saves | Cost |
|---|---|---|
| Tab's two Claude processes start only when Tab needs Claude (engine Claude, or no local model ready) | 208-224 MB with a local model | none (they start on Claude's first turn) |
| Ask's Claude process starts on the Ask tab, not for text search | ~105 MB | none |
| Claude helpers stop after minutes without use: Tab 15, terminal 10, Ctrl+K/Apply 10, commit/Source Control/plain words 5, Ask 10 | ~100 MB each | the first answer after: 0.8 s instead of 0.6 s (measured) |
| Terminal Tab: one Claude process instead of two | ~100 MB when used | none noticed (it asks after a pause) |
| Ollama keeps Tab's model 30 min after the last suggestion (was 2 h) | 1.1 GB, 90 min sooner | about 1 s, once, after a long pause |
| While Ollama is busy with a chat's model, Claude helps Tab and the slower request is stopped | GPU time for the chat | Claude requests (if set up) |
| Claude Code's options: saved, asked in the background | a 0.3-8 s freeze per window | none |
| `~/.claude.json` (checked every 4 s in every window): read again only when it changed | 50 checks: 8.7 ms instead of ~50 ms | none |
| Ollama's status (every 15 s): only while the window is in front | CPU and wake-ups in the background | none |

After (test copy, idle 60 s after start): **14 processes, 1,078 MB** (before: 17, 1,268 MB). For Adithya's setup this
is 326 MB less right away, and Tab's 1.1 GB model unloaded 30 minutes after he stops typing.

Done in the chat (lib/chat) the same day, from these numbers: a chat off screen with nothing going on for 10 minutes
stops its `claude` process (at most 2 idle ones stay warm; three chats were 367 MB), a streaming answer is redrawn about
15 times a second instead of every frame (its page used 15 % of a core), and a chat on a model on this computer gets a
1,100-character guide to Kural instead of the 18,000-character one (its first message was 36,826 characters: 28 s of
reading on this Mac).

## Plan for later, biggest first

1. **A memory budget for models on this computer.** Ollama keeps up to 3 models loaded and unloads the oldest when a
   new one doesn't fit; on 16 GB a 9B chat model at 32k context (7.8 GB) pushes Tab's model out. Kural knows the
   computer's memory and each model's size: pick the context length by memory (16k on 16 GB), say so before a model
   choice that won't fit next to Tab's, unload the chat's model after some idle minutes (keep_alive), and unload sooner
   when the computer is short of memory (macOS memory pressure, `os.freemem()`).
2. **A process budget for Claude Code.** At most a few `claude` processes in all (chats + helpers); the one unused the
   longest stops first. One-shot helpers (Ctrl+K, commit messages, plain words, Source Control) could share one warm
   process per model instead of one each.
3. **"Kural: Show Memory Use"**: this script's table inside Kural (Kural Settings), with a Stop button for idle chats and
   loaded models, so you can see what takes memory and free it.
4. **Language servers.** VS Code runs two TypeScript servers (~230 MB); a "light" choice could use one
   (`typescript.tsserver.useSyntaxServer`) and stop servers of languages not used for 30 minutes.
5. **Background work at low priority.** Run ripgrep (renames), the router's helper preparation and downloads with a lower
   CPU priority (`os.setPriority`), and do every timer only while the window is in front (done for Ollama's status;
   usage polling next).
6. **The chat page.** Draw only the messages on screen for long chats (the renderers grow with history), and cap the
   streaming frame rate.
7. **Watch it in CI.** Run `bench-memory.js` on the built app in the start-up check (idle after start) and fail when it
   grows more than 20 % over this baseline.
